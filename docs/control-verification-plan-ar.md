**الحالة:** مسودة تنفيذية؛ ليست اعتماد QA أو إذناً بتشغيل FSMS.  
**خط الأساس:** المراجعة على `de6d79d256f2bf078bcb76c1de244710335d796e`.  
**حزمة العمل:** PR #2، فرع `fix/audit-critical`. يجب تسجيل SHA المرشح النهائي في محضر كل اختبار.

## 1. الهدف وحدود القبول

ضبط إصلاح أعطال حفظ المستندات وNCR وحالة الوثائق، وإثبات صحة النتائج وعزل المستخدمين قبل النشر. يُمنع وصف التطبيق بأنه نظام FSMS معتمد بسبب نجاح البناء أو وجود قوالب إجراءات.

- **Verification:** هل يعمل الكود/المخطط وفق متطلبات محددة؟ الدليل: اختبارات وأثر تنفيذ.
- **Validation/UAT:** هل يلبي سير العمل غرض المستخدم الصناعي؟ الدليل: سيناريوهات مصنع ينفذها ممثل الجودة.
- **تصديق ضوابط العملية الغذائية:** دراسة مستقلة يقرّها فريق سلامة الغذاء والجهة الفنية المؤهلة؛ الاختبارات البرمجية لا تثبت صلاحية البسترة أو CIP.

حزمة الإصلاح الحالية لا تشمل إغلاق فجوة الاعتماد الإلكتروني لـHACCP/CAPA، ولا استكمال التتبع أو تحويل محتوى المياه إلى خطة حمضيات مصدقة.

## 6. دليل التنفيذ وإدارة الانحرافات

لكل تشغيل: `Run ID / commit SHA / environment / versions / test ID / expected / actual / result / evidence path / executor / reviewer / UTC time`.

الحالات: لم يُنفذ / ناجح / فاشل / محجوب / غير منطبق بمبرر. لا تُحوّل «محجوب» إلى «ناجح». افتح انحرافاً بمعرف `DEV-APP-###` لكل فشل مع الأثر والاحتواء وRCA وCAPA والمالك والموعد وإعادة الاختبار.

- لا بيانات إنتاج حقيقية في fixtures أو logs أو screenshots.
- اربط صور/تقارير CI بـSHA. لا تعتبر نجاح commit قديم دليلاً على commit أحدث.
- احتفاظ artifact في CI حالياً 30 يوماً؛ انقل أدلة الإصدار المعتمدة إلى مستودع الوثائق المضبوط وفق سياسة الاحتفاظ المعتمدة قبل انتهاء المدة. لم تُحدَّد مدة احتفاظ تنظيمية من تلقاء نفسها.
- CI الجديد يفحص الملفات المتغيرة؛ أخطاء lint التاريخية تظل مفتوحة. npm audit لقطة معلوماتية تظهر الفشل ولا تمنع build وحدها؛ مراجعة التنبيهات شرط إصدار منفصل.
- إعداد branch protection لجعل CI مطلوباً يحتاج تحقق مسؤول المستودع؛ وجود workflow وحده لا يفرض حظر الدمج.

## 7. النشر والتراجع

**قبل النشر:** نفّذ `docs/preflight-document-repair.sql` كقراءة فقط، واحفظ schema/function definitions ونسخة قابلة للاستعادة. سجل DB migration version وEdge revision وFrontend deployment ID السابق والجديد.

**التسلسل:** DB migration الجديد فقط → Edge `parse-document` مع `handler.ts` → smoke test بحساب تجريبي → Frontend → UAT مختصر. لا تستخدم reset الإنتاج ولا تعِد تشغيل تاريخ migrations المتعارض.

**شروط التوقف:** وصول غير مخوّل واحد، نجاح حفظ كاذب واحد، فقد/تغيير نص، تعليق chunking، فشل حفظ NCR، أو عدم توافق عقد API. أوقف المسار المتأثر وافتح انحرافاً فوراً؛ لا تنتظر متوسط أخطاء مقبولاً لخرق سلامة البيانات.

**التراجع:** احتفظ بتعديل الدالة الذي ينهي الحلقة والأعمدة الإضافية؛ لا تُعِد الدالة القديمة المعيبة ولا تسقط أعمدة NCR المحتوية على بيانات. عند خلل Frontend/Function، أوقف الرفع أو ارجع إلى إصدار متوافق مثبت مع الحفاظ على فشل صريح؛ إن لم توجد نسخة آمنة متوافقة فالتعطيل المؤقت أفضل من رجوع نجاح وهمي. أي استعادة بيانات يجب أن تسبقها مقارنة وسجل للكتابات بعد النسخة الاحتياطية.

**بعد النشر:** افحص فوراً ثم بعد 24/48/72 ساعة: نجاح حفظ تجريبي، أخطاء DB/Edge، زمن العملية (سجل median/p95 الفعلي دون اختلاق هدف سابق)، الشكاوى، وثائق دون أجزاء، وعمليات فاشلة تظهر كناجحة. قبول زمن الأداء يُحدد من قياس staging وحجم الملف قبل الإصدار.
