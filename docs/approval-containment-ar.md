# احتواء الاعتماد غير الموثّق — دفعة 3

## المشكلة والدليل

- `src/components/plans/SignatureDialog.tsx` في النسخة السابقة: الاسم وPIN والطابع الزمني مصدرها المتصفح؛ لا تحقق من هوية الموقّع أو صلاحية الاعتماد.
- `src/components/plans/HACCPTables.tsx`: حالة approved كانت تُحفظ مع signature_data مباشرة، وتظهر قبل التأكد من نجاح الحفظ.
- `src/pages/NCReports.tsx`: كتابة verified_by وverified_at واختيار verified مباشرة من قائمة الحالة.
- RLS يقيد ملكية السجل لكنه لا يفوض الاعتماد. التصنيف: High؛ CWE-862 وCWE-807.

## الإصلاح المنفذ وحدوده

إجراء احتواء مؤقت: إزالة التوقيع بالاسم وPIN، ومنع ادعاء الاعتماد في HACCP والـPDF، ومنع تسجيل تحقق CAPA من الواجهة أو عبر INSERT/UPDATE المباشر. يحفظ HACCP كمسودة فقط؛ تظل حالات NCR التشغيلية open / in_progress / closed متاحة. الإغلاق التشغيلي ليس إثبات فاعلية.

Migration: `20260922184249_quarantine_unverified_approvals.sql` بعد migration إصلاح الحفظ. يستخدم SECURITY INVOKER، دون تجاوز RLS؛ تنفيذ الدالة غير متاح مباشرة لأدوار API. الحظر يشمل الكتابات الإدارية العادية أيضاً ولا يستثني service role.

لا تُحذف بيانات الاعتمادات السابقة ولا يعاد اعتمادها. تعرضها الواجهة كغير موثّقة، وتسمح بإرجاع HACCP لمسودة أو NCR لحالة تشغيلية مع إبقاء بيانات التوقيع السابقة دون تعديل. هذا لا يوفر أرشيفاً غير قابل للحذف: صلاحيات حذف السجلات الأصلية لم تتغير. يجب أخذ نسخة احتياطية قبل التطبيق وحفظ الأدلة خارج السجل التشغيلي ضمن سياسة الاحتفاظ.

## التحقق

- 44 اختبار تطبيق ناجح، بينها تحميل سجل HACCP معتمد سابقاً والتأكد أن الواجهة ومنطقة PDF لا تعرضان اعتماداً موثّقاً.
- 17 اختبار PostgreSQL ناجح: رفض INSERT/UPDATE للتوقيع المصطنع، رفض verified وحقول المحقق من الطلب المباشر، نجاح المسودة والمتابعة التشغيلية، RLS بين مستخدمين، تكرار migration، حفظ الأدلة القديمة.
- الاختبارات محلية بمعزل عن الإنتاج؛ لا تثبت صلاحية النشر أو قبول المستخدم.

## بوابة الاستكمال

1. تنفيذ اختبارات Staging بالهويات الفعلية وتطبيقَي الويب والموبايل، بما فيها نسخة عميل قديمة تحاول الاعتماد؛ المتوقع رفض قاعدة البيانات.
2. ضبط صلاحيات Author / Reviewer / Approver خادمياً على مستوى المؤسسة مع فصل المهام؛ لا تعتمد على user_metadata أو اسم مكتوب.
3. بناء سجل أحداث غير قابل لتعديل العميل: هوية موثّقة، وقت خادم، إصدار الوثيقة وبصمته، القرار وسببه ودليل المراجعة/الفاعلية.
4. ربط التوقيع بالإصدار وإبطال اعتماد المحتوى المعدّل وإعادة التحقق من الجلسة عند الإجراء الحساس.
5. اختبار النسخ الاحتياطي والاستعادة، ثم UAT موثق قبل إعادة إتاحة الاعتماد.

النشر: قاعدة البيانات أولاً، ثم الواجهة. لا تتراجع بإزالة الحارس لإعادة تشغيل عميل قديم؛ أعد الواجهة إلى نسخة لا تدّعي الاعتماد واحتفظ بالحظر حتى إصلاح سير العمل.
